# TradingBuddy SOUL 驱动的事件研究与交互体验设计

## 1. 文档状态

- 日期：2026-09-28
- 基线：`origin/main` at `fabb14c`
- 目标产品：https://antiteration.com/
- 参考仓库：https://github.com/Venestiteration/fin-advisor-agent
- 参考重点：`SOUL.md`、`stock_analyzer`、`stock_analysis_responder`、`info_aggregator`、`risk_educator`、`density_controller`

本文描述 TradingBuddy 下一版的产品与技术设计。它覆盖事件级公开动态、渐进式新闻阅读、连续时间线交互和 AI 研究回答质量，但不改变产品的数据来源、访客自带 AI Key、服务端不持久化访客 AI 内容以及“不提供买卖指令”的边界。

## 2. 设计结论

TradingBuddy 不应把参考仓库简化为一套“意图路由”。`SOUL.md` 的核心价值是一个稳定的研究人格和回答纪律：在信息混乱时先形成判断，在用户焦虑或急于行动时减速，把专业分析翻译成普通人能理解的语言，并始终指出关键矛盾、风险和验证条件。

本次设计把这个核心转化为四层提示词体系：

1. **产品宪法层**：证据约束、隐私边界、投资安全边界和禁止事项；
2. **研究思维层**：参考 `SOUL.md` 的“理性大脑”和股票分析维度；
3. **任务模板层**：今日报告、事件解读和连续追问各自独立的任务提示词；
4. **结构化输出层**：可校验、可降级、可稳定渲染的 JSON Schema。

意图识别只作为回答组织的辅助信息，不是系统核心，也不触发未经证据支持的数据调用或用户画像推断。

## 3. 核心目标

用户进入一个标的后，应在不调用 AI 的情况下先得到三个可读答案：

1. 今天真正发生了什么重要变化；
2. 已知信息为什么值得关注，可能通过什么路径影响当前标的或用户已确认的投资判断；
3. 哪些是事实、哪些是推断、哪些仍无法确认。

当用户主动点击“展开 AI 解读”或继续追问时，系统再使用访客自己的 AI 配置，对当前事件簇和相关证据做更深入解释。AI 失败不能影响规则报告、原始新闻、行情和来源的阅读。

## 4. 不直接照搬的参考规则

以下内容属于 `fin-advisor-agent` 的运行环境或更激进的投顾行为，不能直接进入 TradingBuddy：

- 每次回答后强制生成独立 HTML 报告；
- 默认推断用户持仓、亏损状态、风险偏好或认知水平；
- 在风险承受能力未知时给出仓位、止损位、买卖点或具体交易动作；
- 绕过 TradingBuddy 现有证据对象，直接依据搜索摘要或模型记忆输出事实；
- 在服务端保存访客的 API Key、分析结果或对话；
- 把示例中的历史数字、确定性判断和个股结论当作可复用事实；
- 为了形成完整叙事而补写只有标题的新闻正文、原因、主体或数字。

TradingBuddy 只吸收参考仓库的分析人格、思考维度、语言原则、信息密度控制和“帮用户想深一层”的回答方式。

## 5. 产品原则

### 5.1 证据先于叙事

任何事实都必须绑定一个或多个现有 `evidence_id`。没有有效引用的事实不能进入“已知事实”。模型可以提出推断，但必须同时给出引用证据、推断链和不确定性。

### 5.2 结论前置，但结论有边界

回答先说当前最重要的判断和关键矛盾，再展开证据。结论不是交易指令，也不能把相关性写成因果性。证据不足时，结论应明确为“暂时只能确认到这里”。

### 5.3 说人话，但不牺牲准确性

专业名词第一次出现时使用普通语言解释。数字不能只罗列，要说明它相对昨天、历史区间或当前问题意味着什么。没有可靠参照时，不强行类比。

### 5.4 帮用户想深一层

除回答表面问题外，系统应补充一个最相关的盲点、反向证据或验证条件。补充内容仍必须来自当前证据包，不允许扩展成无证据的宏大判断。

### 5.5 AI 是解释层，不是数据层

事件聚合、排序、状态判断和默认报告由确定性代码生成。AI 只在用户主动触发时解释这些内容，不负责发现或保存新的事实。

## 6. 总体架构

```text
公开来源同步 + 行情数据
          │
          ▼
现有 evidence / public_dynamics
          │
          ▼
Research Event Cluster（二次事件聚合，确定性）
          │
          ├── Daily Research Brief（默认规则报告，不调用 AI）
          │
          ├── 渐进式事件阅读与来源追溯
          │
          └── 用户主动触发 AI
                    │
                    ▼
       SOUL Prompt Stack + Context Selector
                    │
                    ▼
       严格 Schema + 证据/数字/冲突校验
                    │
                    ▼
             浏览器本地结果
```

现有 `public_dynamics` 保留为来源归一化后的第一层事件。新增 `Research Event Cluster` 是读取时的第二层逻辑聚合，用于把同一事项的公告、媒体转载和相关行情信号放入一个研究事件，不新增必须持久化的 AI 结果表。

## 7. 事件级聚合

### 7.1 输入

聚合器使用：

- 最近 24 小时的 `public_dynamics`；
- 每条动态关联的 `public_dynamic_evidence`；
- 当前标的最新行情和最近交易日行情事实；
- 来源同步状态和数据覆盖说明；
- 用户已确认 thesis 中的观察变量，只用于提高相关性，不改变事实。

市场异常只能作为同日的“相关行情表现”附着到事件，不能自动被写成新闻导致了涨跌。

### 7.2 聚合规则

公告继续使用现有规范化标题、上海业务日和数字一致性规则。

媒体新闻在现有 provider identity 去重之上增加事件相似度聚合：

- 标的代码相同；
- 发布时间相差不超过 36 小时；
- 标题规范化后二元字符集合相似度达到阈值，或主体、事项词和公告类别高度一致；
- 数字和否定词不一致时仍可进入候选事件，但必须标记 `conflict_status=possible`，不能把冲突值合并成单一事实；
- 仅有宽泛行情榜单且没有明确描述当前标的事项的新闻，不与公司公告强行合并。

公告与新闻允许跨类型关联，但需要共享明确事项词或主体，且时间相邻。关联成功后仍保留每条原始证据及其来源关系。

### 7.3 稳定标识

`cluster_id` 由资产 ID 和成员中最小的现有 `public_dynamics.id` 生成。新同步的动态只会获得更大的数据库 ID，因此为既有事件补充来源时 `cluster_id` 不变；无法安全关联的内容保留为独立事件。若人工修正规则导致一个旧事件被拆分，拆出的新事件允许获得新 ID，但原锚点所在事件继续保留原 ID。

### 7.4 重要性评分

事件排序使用可解释权重：

```text
attention_score =
  0.30 × 与标的和已确认判断的相关性
+ 0.25 × 事项潜在重要性
+ 0.20 × 时效性
+ 0.15 × 证据质量
+ 0.10 × 独立来源佐证
```

规则要求：

- 一级公告提高证据质量，但不能因为来源权威就自动推导影响；
- 多个转载不等于多个独立来源；
- 仅标题降低完整度；
- 来源冲突降低结论置信度，但不隐藏事件；
- 用户 thesis 只影响“与当前判断的相关性”，不能提高事实置信度；
- 每个因子和贡献值随 API 返回，便于测试和解释。

## 8. 默认“今日最重要的变化”报告

### 8.1 行为

进入标的、切换标的或刷新后，前端直接展示确定性报告，不调用模型。报告选择最高分事件作为主事件，并最多带两个相关事件作为背景。没有可靠事件时，明确展示覆盖状态和行情事实，不用旧新闻填充“今日变化”。

### 8.2 数据结构

```json
{
  "status": "available | empty | limited | failed",
  "window_start": "ISO-8601",
  "window_end": "ISO-8601",
  "headline": "string",
  "core_conclusion": "string",
  "facts": [
    {
      "claim": "string",
      "evidence_ids": ["string"],
      "content_status": "title_only | excerpt | full"
    }
  ],
  "why_it_matters": [
    {
      "explanation": "string",
      "basis": "rule | evidence",
      "evidence_ids": ["string"]
    }
  ],
  "impact_paths": [
    {
      "path": ["事项", "可能影响的经营或预期变量", "需要观察的结果"],
      "confidence": "low | medium",
      "evidence_ids": ["string"]
    }
  ],
  "inferences": [
    {
      "claim": "string",
      "uncertainty": "string",
      "evidence_ids": ["string"]
    }
  ],
  "unknowns": ["string"],
  "watch_signals": ["string"],
  "sources": [
    {
      "evidence_id": "string",
      "title": "string",
      "publisher": "string",
      "source_url": "string",
      "content_status": "title_only | excerpt | full",
      "relation": "primary | corroborating | related"
    }
  ],
  "coverage": {
    "event_count": 0,
    "source_count": 0,
    "source_status": "complete | partial | failed",
    "limitations": ["string"]
  },
  "conflict_status": "none | possible"
}
```

### 8.3 规则报告边界

- `title_only` 的事实只允许复述标题明确表达的主体和事项；
- 规则模板可以解释公告类别通常需要关注的变量，但必须用“需要观察”表达，不能写成该影响已经发生；
- 行情同时异动时只能写“同一时段行情出现变化”，不能写“受该消息影响”；
- `why_it_matters` 没有直接证据时标记 `basis=rule`；
- 没有足够信息形成影响路径时，`impact_paths` 为空，并在 `unknowns` 说明缺口；
- 冲突事实逐条保留，不能计算平均值或选择更吸引人的版本。

## 9. SOUL 提示词体系

### 9.1 产品宪法层

产品宪法拥有最高优先级，所有任务共用：

- 你是 TradingBuddy 的研究解释层，是用户的“理性大脑”，不是荐股机器；
- 只能使用传入上下文中的证据和行情；
- 事实必须引用有效 `evidence_id`；
- 不从浏览记录、默认资产类型、语气或问题措辞推断持仓、成本、风险偏好；
- 只有用户明确表达或已确认 thesis 中的内容才能作为用户判断；
- 不给买卖指令、目标价、仓位比例或确定性收益判断；
- 只有标题时，不补写正文、数字、原因或结果；
- 冲突必须保留，信息不足必须降级；
- 使用普通用户能理解的语言，结论前置，但结论不能超过证据。

### 9.2 研究思维层

参考 `SOUL.md` 和 `stock_analyzer`，模型在内部按以下顺序思考，但不向用户暴露内部标签：

1. 发生了什么，哪些是已确认事实；
2. 当前标的自身的经营或治理变量是否真的变化；
3. 当前价格和行情反映了什么，但不把价格变化当作原因；
4. 行业、政策或竞争环境是否提供了可验证的外部路径；
5. 市场行为与基本信息是否存在矛盾；
6. 用户已确认的 thesis 哪一部分被支持、挑战或尚未触及；
7. 最重要的未知项是什么，下一步看到什么信号才应更新判断。

这七步是内部分析框架，不要求每次回答机械输出七段。对外只保留最相关的两个到四个板块。

### 9.3 任务模板层

建立三个独立且版本化的任务提示词：

#### 今日事件报告

目标是解释当天主事件和相关事件。输出核心结论、事实、影响路径、推断、未知项和观察信号。不能输出交易建议。

#### 单事件深度解读

围绕用户展开的事件簇，解释来龙去脉、为什么重要、对当前标的和已确认 thesis 的可能影响。来源冲突单独成段。

#### 连续追问

先直接回答当前问题，再补充一个最相关的盲点或验证条件。避免重复上一轮背景。只有当前问题确实需要时，才引用其他事件或历史对话。

### 9.4 表达与密度层

吸收 `SOUL.md`、`risk_educator` 和 `density_controller` 的有效原则：

- 第一段必须给出可理解的核心结论和关键矛盾；
- 展开内容使用两个到四个差异明确的口语化小标题；
- 每个数字紧跟含义或参照；
- 专业术语第一次出现时翻译；
- 简单问题给短答案，复杂问题才展开；
- 一个回答最多提供一个后续核验问题；
- 不强制生成图表；图表由产品已有数据可视化承担；
- 不使用情绪化鼓励、确定性安慰或“拿住就行”等表达。

结构化 JSON 中不直接保存 Markdown 格式。前端根据字段语义渲染标题、事实、推断和引用，避免模型用格式绕过验证。

## 10. AI 结构化输出与校验

### 10.1 输出结构

AI 报告在默认报告基础上增加：

```json
{
  "answer_mode": "daily_brief | event_analysis | follow_up",
  "core_conclusion": "string",
  "key_tension": "string",
  "sections": [
    {
      "title": "string",
      "body": "string",
      "evidence_ids": ["string"]
    }
  ],
  "facts": [],
  "impact_paths": [],
  "inferences": [],
  "unknowns": [],
  "watch_signals": [],
  "thesis_relationship": {
    "status": "supports | challenges | unrelated | insufficient",
    "explanation": "string",
    "evidence_ids": ["string"]
  },
  "follow_up_question": "string",
  "confidence": "low | medium | high",
  "safety_boundary": "string"
}
```

### 10.2 程序校验

在现有引用校验上增加：

- 所有 `facts` 必须至少有一个有效引用；
- 引用仅标题证据的事实必须是标题的保守转述，不能包含证据中不存在的新数字；
- 数字事实中的数字必须能在至少一条引用证据或行情快照中找到；
- `sections` 中出现的新事实也必须有引用；
- 只有推断可以使用“可能、如果、需要观察”等条件语言，并必须填写不确定性；
- 事件存在 `conflict_status=possible` 时，输出必须在 `unknowns` 或单独段落保留冲突，且 `confidence` 不能为 `high`；
- 无有效事实时，结论强制降级为信息不足；
- 出现买卖、加减仓、目标价等指令式表达时，拒绝该结果并进行一次修复调用；
- 修复仍失败时返回规则报告，不让整个页面失败。

## 11. AI 上下文选择

上下文选择是回答稳定性的关键，但不以复杂意图路由为核心。

### 11.1 固定上下文

- 当前标的代码和名称；
- 最新行情快照及其时间；
- 当前展开的事件簇和全部成员证据；
- 当前默认日报中的主事件；
- 用户已确认的最新 thesis；
- 产品安全边界。

### 11.2 按问题选择的上下文

从最近 90 天事件中按标的、关键词、类别、发布时间和当前事件关联度选择最多 12 条证据。当前事件的全部证据优先，不相关的旧背景不进入提示词。

浏览器最多传入最近 6 条本地对话。服务端只保留与当前问题或当前事件相关的消息，并控制总字符数。历史回答中的事实不能成为新事实来源，必须回到原始证据。

### 11.3 轻量问题模式

可以在本地代码中识别“发生了什么、标的分析、条件规划、情绪问题、概念解释”五种回答重点，但该结果只决定内容密度和段落顺序：

- 不自动加载新的外部数据；
- 不推断持仓状态；
- 不覆盖证据约束；
- 不强制套用固定模板；
- 不把用户问题改写成具体交易建议。

## 12. API 设计

新增接口保持向后兼容：

### `GET /api/assets/{asset_id}/research-brief?hours=24`

返回默认规则报告、事件簇列表、来源覆盖和行情关联信息。`hours` 第一版固定为 24。

### `GET /api/assets/{asset_id}/research-events/{cluster_id}`

返回一个事件簇的完整聚合信息、成员动态、全部证据和冲突状态。

### `POST /api/research-brief/stream`

请求包含 `asset_id`、`cluster_id` 和可选问题。访客模型配置继续从请求头读取。返回 SSE 状态和经校验的结构化 AI 解读，不写入 SQLite。

### `POST /api/chat/stream`

兼容现有请求，并增加可选 `cluster_id`。当它存在时，以事件簇而非单条 `dynamic_id` 为主要上下文。`dynamic_id` 继续兼容旧前端。

## 13. 新闻与事件阅读体验

### 13.1 顶部日报

“今日最重要的变化”不再展示单条标题。默认呈现：

- 核心结论；
- 发生了什么；
- 为什么值得关注；
- 影响路径；
- 尚不能确认的内容；
- 来源数量、覆盖状态和最近更新时间。

“展开 AI 解读”仅在访客已启用 AI 时显示。未启用时提供“查看证据”而不是诱导配置。

### 13.2 事件簇卡片

折叠态展示：标题、时间、事件类型、来源数量、内容完整度、冲突状态和两行摘要。

展开态原位展示：已知事实、解释、推断、未知项、观察信号、参与来源列表以及 AI 解读入口。来源列表显示媒体名、发布时间、内容状态和“打开原文”。

页面一次只展开一个事件簇，切换事件时保留已加载的规则数据；AI 结果按资产和 `cluster_id` 保存在浏览器本地工作区。

### 13.3 状态

- 加载中：保留页面框架和行情，不显示虚假占位结论；
- 无内容：说明 24 小时窗口和来源覆盖，不回填旧内容；
- 来源部分失败：显示已有事件，同时展示覆盖限制；
- AI 失败：保留规则报告和来源，显示可重试错误；
- 来源 URL 不可用：显示证据标题和状态，禁用外链按钮；
- 冲突：在事件标题附近显示低干扰提示，并在展开态列出差异。

## 14. 连续时间线交互

继续使用现有原生 SVG，不引入大型图表库。

### 14.1 数据加载

进入标的时一次请求最多 90 个交易日并在前端缓存。初始视图显示最近 30 个交易日，但不再通过 30/90 日按钮替换数据。

### 14.2 视图模型

图表维护：

```text
view.startIndex
view.endIndex
view.minVisiblePoints
view.maxVisiblePoints
```

滚轮以指针对应的数据索引为中心连续改变可视点数；拖动改变 start/end；双指距离变化控制缩放，双指中心控制锚点。所有结果限制在已加载数据边界内。

### 14.3 页面手势边界

- 只有指针位于图表绘图区且手势主要为横向或缩放时阻止默认行为；
- 普通纵向滚动继续滚动页面；
- 移动端单指纵向滑动不被图表劫持；
- 双指缩放只作用于图表；
- 到达边界时显示短暂提示，不循环或伪造更多数据。

### 14.4 可访问性

提供“缩小时间范围”“扩大时间范围”“向前移动”“向后移动”“重置视图”按钮和实时 aria 状态。数据点继续支持键盘聚焦和 Enter 打开详情。屏幕阅读器可读取当前可视日期范围、最高重要性日期和数据边界。

标签密度根据当前可见点数采样，折线、事件标记和节点位置通过同一坐标函数计算，避免缩放过程中互相错位。

## 15. 失败与降级

| 失败点 | 降级行为 |
|---|---|
| 公开来源同步失败 | 使用已有事件与缓存，显示来源状态 |
| 事件聚合异常 | 回退为现有 canonical dynamics 列表，不丢来源 |
| 行情不可用 | 省略行情关联，不影响事件阅读 |
| AI 未配置 | 只展示规则报告和来源 |
| AI 网络、额度或模型错误 | 展示分类错误和重试入口，规则报告保持可读 |
| AI Schema 校验失败 | 修复调用一次，仍失败则回退规则报告 |
| 浏览器存储不可用 | 本次会话内可用，不持久化 AI 结果 |
| 时间线不足 90 日 | 使用已有范围，并明确边界 |

## 16. 文件职责

预计新增或调整的主要边界：

- `app/services/research_events.py`：二次事件聚合、稳定 cluster ID、排序与冲突状态；
- `app/services/research_brief.py`：默认日报和规则影响模板；

- `app/services/ai.py`：通用模型调用保留，接入新的 Schema 校验器；
- `app/services/research_prompts.py`：组合产品宪法、研究思维和任务提示词；
- `prompts/research_soul.md`：TradingBuddy 版 SOUL，不包含工具调用和交易指令；
- `prompts/daily_brief.md`、`prompts/event_analysis.md`、`prompts/follow_up.md`：任务提示词；

## 17. 验收场景

### 事件聚合

- 两篇标题相近、时间相邻、描述同一事项的新闻只形成一个事件簇；
- 不同数字或否定表达被保留为冲突，不能合成单一事实；
- 公司公告和相关媒体报道可以进入同一事件簇；
- 宽泛榜单新闻不会仅因出现股票代码就与公司事件强行合并。

### 今日报告

- 顶部是多证据事件报告，不是单条标题或摘录；
- 只有标题时不出现证据中没有的数字、原因或结果；
- 行情异动不会被自动写成新闻造成的因果；
- 每个事实、推断和影响路径都能追溯来源；
- 没有 24 小时内容时显示真实空状态。

### AI 分析

- 回答先给结论和关键矛盾，再用普通语言展开；
- 分析能覆盖公司自身、价格/行情、外部环境和市场行为中与问题最相关的维度；
- 不相关维度不会为了凑结构强行出现；
- 当前事件、最新行情、已确认 thesis 和近期相关对话按需进入上下文；
- 不从措辞或默认资产类型推断持仓和风险偏好；
- 冲突时降低置信度并保留差异；
- AI 失败时事件、行情和来源仍可使用。

### 阅读与图表

- 事件卡片可原位展开完整内容和来源；
- 来源可逐条打开原文；
- 加载、空内容、失败、来源不可用和冲突状态完整；
- 桌面滚轮缩放、拖动平移和移动端触摸/双指缩放可用；
- 页面纵向滚动不被图表永久劫持；
- 键盘用户可以缩放、平移、重置并打开数据点。

## 18. 测试策略

### Python

- 事件相似度、跨类型聚合、稳定 ID、数字冲突和错误合并保护；
- 重要性评分的因子贡献与排序；
- 默认报告的标题-only、冲突、空内容和来源失败行为；
- AI Schema、引用、数字、交易指令和置信度校验；
- 上下文相关性、数量上限、thesis 选择和消息裁剪；
- 新 API 的资产隔离、访客 AI 配置与不持久化边界。

### Frontend

- 日报默认渲染和规则/AI 状态切换；
- 事件簇折叠、单一展开、来源列表和外链；
- AI 失败后规则内容仍存在；
- wheel 锚点缩放、拖动边界、双指缩放和重置；
- 纵向页面滚动与图表手势共存；
- 键盘和 aria 状态。

### 回归

- 现有 Python 与 Node 测试保持通过；
- visitor-AI 的 Key、分析和对话仍只保存在浏览器；
- 公开动态 90 天同步、24 小时重叠、PDF 按需提取和来源健康状态不退化。

## 19. 实施顺序

1. 事件簇和规则日报；
2. SOUL 提示词分层、上下文选择和结果校验；
3. 日报与新闻渐进式阅读；
4. 连续时间线交互；
5. 全链路回归、浏览器验收和生产部署。

每一步都应先增加失败测试，再实现最小闭环，完成独立审查后进入下一步。

## 20. 剩余风险

- 当前媒体主来源覆盖有限，事件聚合只能在已采集内容内判断“最重要”，不能声称覆盖全网；
- 中文标题相似度存在误合并风险，第一版必须偏保守并保留独立事件；
- 规则影响路径只能说明通常需要观察的变量，不能替代公司基本面数据；
- 访客使用不同模型，结构化输出稳定性存在差异，需要严格校验和降级；
- 90 日数据边界限制了时间线继续缩小到更长周期，超出范围需后续增加分页或分段缓存；
- `SOUL.md` 中部分表达和交易规划规则与 TradingBuddy 的安全边界不兼容，后续同步参考仓库时必须继续经过人工筛选，不能自动覆盖产品宪法层。
